# 고객 POC 진행 절차

DSP는 고객 POC에서 흔한 문제를 해결하기 위해 설계되었습니다. 정상적이거나 폐쇄된 고객 네트워크에서는 짧은 평가 기간 동안 충분한 탐지 사례가 발생하지 않을 수 있습니다.

목표는 또 하나의 공격 Framework를 만드는 것이 아닙니다. 통제된 활동을 사용해 **XDR/NDR의 탐지와 조사 과정을 고객이 직접 확인하고 반복해서 검증할 수 있게 하는 것**입니다.

## 권장 POC 흐름

```mermaid
flowchart LR
    A[승인된 Target CIDR] --> B[Discovery]
    B --> C[Controlled DSP Scenarios]
    C --> D[NDR / XDR Visibility]
    D --> E[Detection Review]
    E --> F[Evidence]
    F --> G[필요 시 XDR Case Demo]
```

실제 고객 POC에서는 다음 흐름을 권장합니다.

1. 승인된 CIDR, 제외 대상, Test Window를 합의합니다.
2. 내부 호스트에서 실행할 필요가 없다면 `local` + `normal`로 시작합니다.
3. DSP를 실행하고 실제 생성된 활동과 실행 기록을 확인합니다.
4. 같은 시간대와 호스트를 XDR/NDR 콘솔에서 확인합니다.
5. Matching Detection ID, Screenshot, Note를 기록합니다.
6. XDR 플랫폼이 관련 Signal을 하나의 Case로 연결했다면 Case 타임라인을 고객 검증 자료에 포함합니다.

<Note>
`dsp run`은 대상 확장, 탐색, 시나리오 순서 결정, 실행, Event Store 기록, 검증, 보고를 한 번에 처리합니다. 위 그림은 고객 POC의 전체 흐름을 보여주며 각 단계가 별도 CLI 명령이라는 뜻은 아닙니다.
</Note>

## Operator가 실제로 결정하는 세 가지

| 결정 | 권장 시작값 |
| --- | --- |
| Activity를 어디서 발생시킬 것인가? | `local` |
| 어떤 Network가 Scope인가? | `--target-net <AUTHORIZED_CIDR>` |
| Target Coverage를 얼마나 넓힐 것인가? | `normal` |

`high`는 더 넓은 Host Coverage가 의도된 경우에만 사용하세요. 대상별 Volume은 `normal`과 같고 더 많은 발견 Target으로 범위만 확장합니다.

## Webshell Mode가 필요한 경우

POC Activity를 고객 Network **내부**의 명시적으로 승인된 Test Host에서 발생시켜야 한다면 검증된 JSP/PHP Webshell Provider를 사용할 수 있습니다. Internal Scan, DNS, Web, Identity Service, Protocol, Host Behavior Activity를 외부 DSP Host보다 실제 환경에 가까운 위치에서 생성할 수 있습니다.

현재 Release에서 ASPX/Windows IIS는 Preview 상태입니다.

## 세 종류의 검증 자료를 구분해서 보기

| 계층 | 질문 | 확인 자료 |
| --- | --- | --- |
| DSP 실행 | DSP가 의도한 활동을 생성했는가? | `traffic_summary.json`, Event Store, `report.md` |
| 탐지 | XDR/NDR에서 해당 활동이 탐지 또는 관찰되었는가? | Detection/Alert ID, 시간, 호스트 |
| 조사 | 관련 Signal이 의미 있는 XDR Case로 연결되었는가? | Case ID, 타임라인, 화면 캡처, 분석가 메모 |

이 세 계층을 분리하면 DSP 자체가 증명하는 범위를 과장하지 않을 수 있습니다.
